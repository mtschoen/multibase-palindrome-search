# Verification

This records what was checked, how, and what remains weak. The goal is that a
reader can decide for themselves how much to trust the bounds in RESULTS.md.

## The chain of claims

1. Every integer with L hex digits that is palindromic in base 2 and base 16 is
   generated by the orbit construction for some leading-bit width b, exactly
   once, and nothing else is generated.
2. The Gray-code enumeration visits every assignment of the free orbits exactly
   once, across all threads.
3. The full decimal palindrome check is correct for all values below 2^256.
4. The prefilter never rejects a value that the full check would accept.
5. The incremental mod-1000 residue used by the prefilter equals the true
   residue at every step.

## Evidence per claim

**Claim 1, enumeration.** The argument is a proof rather than a heuristic: both
palindrome conditions are involutions on bit positions, the conjunction says
bits are constant on orbits, and the padding above the leading digit together
with the top bit pin down the length. The implementation has no length-specific
logic. Empirically, three structurally different programs agree on the complete
list of base 2 plus base 16 palindromes:

| Comparison | Range | Count | Result |
|---|---|---|---|
| tripal_hex (mirror halves, bit-reverse check) vs Python string reversal over every integer | below 16^6 | 196 | identical |
| tripal_hex vs tripal128 (orbits, 128-bit) | up to 10 hex digits | 2,852 | identical |
| tripal128 vs tripal_wide (orbits, 256-bit limbs) | up to 20 hex digits | 2,800,292 | identical |
| tripal_wide, 8 threads vs 4 threads | up to 10 and 20 hex digits | as above | identical |

The leading-digit classification that emerges (1; 3; 5 or 7; 9 or F) matches
Regan's independent case analysis.

**Claim 2, partition.** Thread ranges are computed as contiguous slices of each
group's index range, so they cannot overlap, and every run prints candidates
visited equal to candidates planned. The Gray-code start value for a slice is
built from the Gray code of its first index; agreement of the pair lists across
different thread counts exercises this.

**Claim 3, full decimal check.** `tripal_wide selftest` compares the 256-bit
check against a 64-bit reference on every integer below 2^20, and against
string reversal on 30,800 random decimal strings of every length from 1 to 77
digits, half of them forced palindromic. Zero disagreements.

**Claim 4, prefilter soundness.** By construction the prefilter has only one
rejecting path: when the first three decimal digits, recovered exactly, do not
mirror the last three. Every uncertain situation (digit-count boundary, estimate
within 1e-6 of an integer, numbers under three digits) returns "pass". The
double estimate uses the top 128 bits of the value, so its relative error is
about 1e-15 against a tolerance of 1e-6. Empirically, the self-test shows zero
rejections of 15,400 random palindromes, and `tripal_wide verify 1 30` checks
every one of 2,863,442,596 candidates: among the 3,835,478 whose first and last
three decimal digits genuinely mirror, the prefilter rejected none.

**Claim 5, incremental residue.** `tripal_wide verify 1 30` recomputes the
residue directly for every candidate and compares: zero mismatches over
2,863,442,596 candidates across all 120 groups up to 30 hex digits.

## The GPU port

`src/tripal_cuda.cu` reimplements the enumeration and adds a two-stage device
prefilter, so it was checked against the CPU programs on each point:

| Check | Range | Result |
|---|---|---|
| `tripal_cuda all` candidate list vs `tripal_wide pairs` | up to 20 hex digits | identical, 2,800,292 entries |
| `tripal_cuda 1 32` hits and candidate count vs CPU | up to 32 hex digits | 5 single-digit hits, 11,453,508,260 candidates |
| stage-1 survivors with genuinely mirrored 3-digit ends vs `tripal_wide verify` count | up to 30 hex digits | 3,835,469 + 9 short numbers = 3,835,478, equal |
| stage-2 survivors with genuinely mirrored 9-digit ends vs `tripal_wide verify` count | up to 32 hex digits | 20 = 20, equal |

The two survivor comparisons are the substantive ones: they show that neither
device stage ever rejected a candidate whose end digits truly mirror, which is
the only way a stage could lose a palindrome. The 9 short numbers are
candidates under six decimal digits, which the CPU rule counts with overlapping
digits and the GPU host classifies separately; the Python check in the session
confirmed exactly 9 such numbers.

Fall-through behaviour is as designed and conservative: numbers with 18 or 19
decimal digits have no middle digits between the first and last nine, so the
rounding test passes them all to the host, and large groups pass about 6 in
10 million.

## GPU counter regression

The original GPU survivor counter was 32 bits while one launch could visit
`2^38` candidates. In `all` mode, a group with `2^33` survivors would wrap the
counter to zero and bypass the overflow check. Host-side visited accounting
could still report the planned range. The small `all 1 20` comparison did not
reach this boundary.

The counter, atomic slot, device allocation/readback and host group totals now
use 64 bits. A launch has at most `2^38` survivors, so this counter cannot wrap.
The regression initializes the actual kernel counter to `2^32 - 4`, processes
eight survivors, and requires `2^32 + 4` with an untouched four-entry buffer.
The old code returned 4 and overwrote the sentinels. A second check compares
all 32 candidates of a small group with independent numeric enumeration at
buffer capacities 32 and 3; the latter forces repeated production-path splits.
Compute Sanitizer reported zero memory errors. Fresh large-run results are in
[RESULTS.md](RESULTS.md).

## Exact pruning proof and independent checks

The four complete binary/hex families are ordinary hex palindromes over
`{0,1}`, `{0,3}`, `{0,2,5,7}`, and `{0,6,9,F}`, with endpoints respectively
`1`, `3`, `5/7`, and `9/F`. For `m = ceil(L/2)`, their sizes are
`2^(m-1)`, `2^(m-1)`, `2^(2m-1)`, and `2^(2m-1)`.

For each independent hex position `j`, use weight
`16^j + 16^(L-1-j)`, counting an odd center once. After assigning `d` outer
positions, let `A` be their value and `U` the maximum completion. Positive
weights make `[A,U]` an exact enclosing interval. Every unassigned weight is
divisible by `16^d`, so every completion equals `A` modulo `2^(4d)`.

If the endpoints have equal decimal length and share `k` leading digits, every
integer between them shares that prefix. A decimal palindrome must therefore
equal its reversed prefix modulo `10^k`, and hence modulo `2^k`. With `k` capped
by `4d`, a mismatch with `A` proves that no completion can be a decimal
palindrome. Decimal-length crossings pass conservatively. Disjoint rejected
subtrees plus examined leaves account for every original assignment. This is
an all-length argument for safe rejection; it does not establish nonexistence
beyond ranges whose computation completed.

Independent unrestricted hex-half enumeration followed by binary string
reversal checks the Python candidate sets through eight hex digits. Tests also
check partial intervals, odd centers, decimal-length boundaries and fixed-bit
caps with actual decimal-palindrome witnesses. Native tests compare all
accounting/node/leaf fields with Python and check decimal conversion against
Python big integers, including `2^256 - 1`. The C representation uses five
base-`10^19` chunks and a 79-byte decimal buffer. See the experiment notes for
commands and the optional bucket predicate's separate conservatism argument.

## Remaining limits

- **No positive control.** No non-trivial hit exists to plant, so the full
  pipeline has never produced a hit beyond the single digits, which bypass the
  prefilter. The verify mode's end-digit check is the closest substitute.
- **One machine.** CPU enumeration used clang 22 and `-march=native`; the
  GPU rerun used nvcc, and the exact searches used Python and clang. All ran
  on the same x86-64 machine. The C code uses `unsigned __int128`, inline
  `divq` on x86-64, and compiler-rt division helpers. A reproduction with GCC,
  on ARM, or without `-march=native` would be valuable.
- **Verify mode stops at 30 hex digits.** The incremental residue and prefilter
  were asserted per candidate up to 30 hex digits, not through 38. The code path
  is identical for larger groups, but the assertion was not run there because
  verify mode is about ten times slower.
- **A real bug was found during development.** The digit buffer in the decimal
  routines was sized for 81 digits while the chunked extraction can write 95;
  the optimized self-test crashed on 77-digit inputs. The search path never
  produced values large enough to trigger it, but it is a reminder that the
  code was written in one session.
- **Self-test randomness** uses the C library `rand()`, which is weak. The
  random strings are only used to compare two implementations against each
  other, so weak randomness cannot produce a false pass, but it limits how
  much of the input space the test explores.

## Reproducing the verification

```
make check                    # self-tests, pair-list agreement, verify mode to 24 hex digits
bin/tripal_wide verify 1 30   # the full verify run reported above, about 16 s on 16 cores
.\build_cuda.bat check       # GPU boundary and forced-splitting regressions on Windows
python -B -m unittest experiments.test_exact_pruning experiments.test_exact_pruning_native
```
